# ప్లాట్‌ఫామ్‌గా ప్రభుత్వం (GaaP)

ప్లాట్‌ఫామ్‌గా ప్రభుత్వం (Government as a Platform) అనేది నోటిఫికేషన్ సేవ, చెల్లింపు సేవ, గుర్తింపు సేవ వంటి ఉమ్మడి, పునర్వినియోగ భాగాలను కేంద్రంగా ఒక్కసారే నిర్మించే వ్యూహం; అప్పుడు వందలాది ప్రభుత్వ సేవలు ఎవరికి వారు నిర్మించుకోకుండా వాటిని వాడుకుంటాయి. ఇది ప్రజా డిజిటల్ మౌలిక సదుపాయాలను ప్లాట్‌ఫామ్ ఆర్థిక శాస్త్ర సమస్యగా మలుస్తుంది: విలువ ఏదో ఒక్క అనుసంధానంలో కాదు, దాన్ని అవలంబించే *తదుపరి* బృందానికి ఉపాంత వ్యయం సున్నాకు చేరడంలో ఉంది.

## ఇది ఎందుకు ముఖ్యం

GDS ఈ వ్యూహాన్ని 2015 "Government as a Platform" ప్రచురణలో అధికారికంగా నిర్దేశించింది: చెల్లింపులు తీసుకోవడం, వినియోగదారు నోటిఫికేషన్, గుర్తింపు ధ్రువీకరణ, చిరునామా శోధన వంటి అవే సామర్థ్యాలను ప్రభుత్వం సేవ తర్వాత సేవలో విడివిడిగా నిర్మిస్తోందని, ప్రతిదీ దాని స్వంత సేకరణ, భద్రతా మదింపు, కొనసాగుతున్న సపోర్ట్ భారాన్ని మోస్తోందని వాదించింది. ప్రత్యామ్నాయం, ఒక్కసారి ఉన్నత ప్రమాణంలో నిర్మించి అన్నిచోట్లా పునర్వినియోగించే కొద్ది ఉమ్మడి ప్లాట్‌ఫామ్‌లు: ఇమెయిళ్లు, టెక్స్ట్ సందేశాలు, ఉత్తరాలు పంపడానికి GOV.UK Notify, ఆన్‌లైన్ చెల్లింపులు తీసుకోవడానికి GOV.UK Pay, గుర్తింపు ధ్రువీకరణకు GOV.UK One Login (మునుపటి GOV.UK Verify గుర్తింపు కార్యక్రమానికి వారసుడు). ఈ ప్లాట్‌ఫామ్‌లు చేరిన స్థాయి వ్యూహం పనిచేసిందనడానికి స్పష్టమైన సాక్ష్యం: GOV.UK Pay సుమారు 1,800 సేవల్లో £10 బిలియన్ల పైగా లావాదేవీలను ప్రాసెస్ చేసింది; మొదటి £1 బిలియన్‌కు సుమారు నాలుగేళ్లు పట్టగా, ఇప్పుడు అంతే మొత్తాన్ని సుమారు ఐదు నెలల్లో చేస్తోంది; GOV.UK Notify 1,500కు పైగా ప్రభుత్వ సంస్థల తరఫున 9 బిలియన్లకు పైగా సందేశాలు పంపింది. వీటిని అవలంబించిన ప్రతి సేవా తన స్వంత చెల్లింపు గేట్‌వేను లేదా సందేశ పైప్‌లైన్‌ను నిర్మించి, భద్రపరచి, నిర్వహించే భారాన్ని తప్పించుకుంది.

## గణితం

```
Build cost per service (no platform) = N services × cost to build,
  secure-assess, and run one payment/notification/identity system

Platform cost = fixed platform build cost
              + marginal cost per adopting service (integration,
                configuration, ongoing platform-team support)

Reuse breaks even once:
  platform build cost < N × (per-service build cost − marginal
  integration cost)

For a mature platform, marginal cost per additional adopter approaches
the transaction/message fee alone — the fixed cost is amortized across
the whole government estate, not one department's budget, which is
why GaaP components are usually funded centrally rather than charged
at full cost-recovery to early adopters.
```

## ఉదాహరణ సహిత పరిష్కారం

**చెల్లింపు గేట్‌వే నిర్మించే బదులు GOV.UK Payని అవలంబించే స్థానిక సంస్థ**:

```
Build-your-own estimate:
  PCI-DSS compliance work + integration + ongoing maintenance
  ≈ £85,000 build + £22,000/year maintenance

GOV.UK Pay adoption:
  Integration effort ≈ £12,000 (developer time)
  Transaction fees: government-to-citizen card payments typically
  charged at a small percentage + fixed fee per transaction, no
  separate PCI-DSS burden carried by the council
  ≈ £12,000 one-off, ongoing cost variable with volume, not fixed

First-year saving ≈ £85,000 − £12,000 = £73,000, before counting the
avoided £22,000/year maintenance and the avoided compliance risk of
holding card data in a council-run system at all — this second
category is the security value covered in
public-sector-cybersecurity-value.
```

ఆ £73,000ను ఇప్పుడు GOV.UK Payని వాడే సుమారు 1,800 సేవలకు విస్తరిస్తే, ప్రభుత్వమంతటా తప్పించుకున్న నిర్మాణ వ్యయం వందల మిలియన్లలో ఉంటుంది. వ్యూహం విలువ నిజంగా ఉన్నది ఏదో ఒక అనుసంధానంలో కాదు, ప్లాట్‌ఫామ్ ఆర్థిక శాస్త్రంలో.

## సాఫ్ట్‌వేర్ ఇంజనీరింగ్‌తో సంబంధం

ప్లాట్‌ఫామ్‌గా ప్రభుత్వం [ప్రభుత్వంలో నిర్మించాలా కొనాలా](../ప్రభుత్వంలో-నిర్మించాలా-లేదా-కొనాలా/)కు నేరుగా వాదన: మదింపైన, బాగా నడిచే ఉమ్మడి భాగం ఉన్నప్పుడు, ప్రత్యేకంగా సమానమైనదాన్ని నిర్మించడం [ఖర్చుకు తగిన విలువ](../డబ్బుకు-తగిన-విలువ/) దృష్ట్యా అరుదుగా మెరుగైన ఎంపిక, అది దాదాపు నిర్వచనం ప్రకారమే [డిజిటల్ సర్వీస్ స్టాండర్డ్](../డిజిటల్-సర్వీస్-స్టాండర్డ్/) 13వ అంశంలో ("ఓపెన్ స్టాండర్డ్‌లు, సాధారణ భాగాలు, నమూనాలను వాడండి, వాటికి తోడ్పడండి") విఫలమవుతుంది. ఇది [ప్రభుత్వ ఐటీలో మొత్తం యాజమాన్య వ్యయం](../ప్రభుత్వ-it-లో-మొత్తం-యాజమాన్య-వ్యయం/) స్వరూపాన్ని కూడా మారుస్తుంది: ప్లాట్‌ఫామ్ అవలంబన పెద్ద మూలధన, నిర్వహణ పద్దును చిన్న, వినియోగ-ఆధారిత నిర్వహణ వ్యయంతో మార్చుకుంటుంది; అది అంచనా వేయడం సులభం, సేవను నిలిపివేసినప్పుడు నిధులు ఆపడం సులభం. భాగాల ఓపెన్ పునర్వినియోగానికి [ఓపెన్ డేటా విలువ](../ఓపెన్-డేటా-విలువ/)లో బంధువు ఉంది: రెండూ ప్రభుత్వం ఒక్కసారి ఉత్పత్తి చేసేదాన్ని విభాగపు ఆస్తిగా కాక ఉమ్మడి మౌలిక సదుపాయంగా చూసే వ్యూహాలు.

## సాధారణ లోపాలు

- **నీడ పునర్నిర్మాణం**: ప్లాట్‌ఫామ్ ఆన్‌బోర్డింగ్ ప్రక్రియ స్వయంగా చేయడం కన్నా నెమ్మదిగా ఉన్నందున బృందాలు మౌనంగా తమ స్వంత చెల్లింపు లేదా నోటిఫికేషన్ అనుసంధానాన్ని నిర్మిస్తాయి; ఇది సాంకేతిక సమస్య కాదు, పాలనా ఘర్షణ సమస్య, మొత్తం వ్యూహం ఆధారపడే పునర్వినియోగ ఆర్థిక శాస్త్రాన్ని మౌనంగా క్షీణింపజేస్తుంది.
- **ప్లాట్‌ఫామ్ బృందానికి అది సృష్టించే విలువకు తగినంత నిధులు ఇవ్వకపోవడం**: విలువ వాడే విభాగాలకు చేరుతుంది, వ్యయం ప్లాట్‌ఫామ్ బృందంపై ఉంటుంది; నిధులు కేంద్రీకృతమై రక్షించబడకపోతే ఇది దీర్ఘకాల తక్కువ పెట్టుబడి ప్రమాదాన్ని సృష్టిస్తుంది, ఇది ఉమ్మడి వనరుల విషాదానికి ఒక రూపం.
- **ప్లాట్‌ఫామ్ విజయాన్ని వినియోగంతో మాత్రమే కొలవడం**: అవలంబన సంఖ్యలు (ఆన్‌బోర్డ్ అయిన సేవలు, పంపిన సందేశాలు) ముందస్తు సూచిక, విలువకు రుజువు కాదు; అసలు పరీక్ష పైన చూపిన తప్పించుకున్న-నిర్మాణ-వ్యయం, తప్పించుకున్న-ప్రమాదం లెక్క.
- **"ప్లాట్‌ఫామ్"ను "మోనోలిత్"కు పర్యాయపదంగా చూడటం**: GaaP భాగాలు ప్రతిదీ ఇరుకైన, స్థిరమైన ఇంటర్‌ఫేస్‌తో ఒక పనిని బాగా చేయడం వల్ల విజయవంతమవుతాయి; సంబంధం లేని సామర్థ్యాలను ఒకే "ప్లాట్‌ఫామ్"లో కట్టేయడం ప్రత్యేక-నిర్మాణ సమస్యను వేరే స్థాయిలో తిరిగి సృష్టిస్తుంది.
