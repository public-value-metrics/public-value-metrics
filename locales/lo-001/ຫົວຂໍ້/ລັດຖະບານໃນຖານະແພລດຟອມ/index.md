# ລັດຖະບານໃນຖານະແພລດຟອມ (GaaP)

ລັດຖະບານໃນຖານະແພລດຟອມ (Government as a Platform) ແມ່ນຍຸດທະສາດການສ້າງອົງປະກອບທີ່ໃຊ້ຮ່ວມກັນ ແລະ ນຳກັບມາໃຊ້ໄດ້ — ບໍລິການແຈ້ງເຕືອນ, ບໍລິການຊຳລະເງິນ, ບໍລິການຢືນຢັນຕົວຕົນ — ໜຶ່ງຄັ້ງຢູ່ສູນກາງ ເພື່ອໃຫ້ບໍລິການຂອງລັດຖະບານຫຼາຍຮ້ອຍບໍລິການນຳໃຊ້ແທນທີ່ແຕ່ລະບໍລິການຈະສ້າງເອງ. ມັນປັບໂຄງສ້າງພື້ນຖານດິຈິຕອນຂອງພາກລັດໃຫ້ເປັນບັນຫາເສດຖະສາດຂອງແພລດຟອມ: ມູນຄ່າບໍ່ໄດ້ຢູ່ໃນການເຊື່ອມຕໍ່ໜຶ່ງຄັ້ງໃດ ແຕ່ຢູ່ທີ່ຕົ້ນທຶນສ່ວນເພີ່ມຂອງທີມ*ຖັດໄປ*ທີ່ນຳໃຊ້ທີ່ເຂົ້າໃກ້ສູນ.

## ເປັນຫຍັງຈຶ່ງສຳຄັນ

GDS ວາງຍຸດທະສາດນີ້ຢ່າງເປັນທາງການໃນສິ່ງພິມ "Government as a Platform" ປີ 2015 ໂດຍໂຕ້ແຍ້ງວ່າລັດຖະບານໄດ້ສ້າງຄວາມສາມາດດຽວກັນ — ການຮັບຊຳລະເງິນ, ການແຈ້ງເຕືອນຜູ້ໃຊ້, ການຢືນຢັນຕົວຕົນ, ການຄົ້ນຫາທີ່ຢູ່ — ແຍກກັນໃນບໍລິການແລ້ວບໍລິການເລົ່າ ແຕ່ລະອັນແບກພາລະຂອງການຈັດຊື້, ການປະເມີນຄວາມປອດໄພ ແລະ ການຊ່ວຍເຫຼືອຕໍ່ເນື່ອງຂອງຕົນເອງ. ທາງເລືອກແມ່ນແພລດຟອມຮ່ວມຈຳນວນນ້ອຍທີ່ສ້າງຕາມມາດຕະຖານສູງໜຶ່ງຄັ້ງ ແລ້ວນຳກັບມາໃຊ້ທຸກບ່ອນ: GOV.UK Notify ສຳລັບສົ່ງອີເມວ, ຂໍ້ຄວາມ ແລະ ຈົດໝາຍ, GOV.UK Pay ສຳລັບຮັບຊຳລະເງິນອອນລາຍ ແລະ GOV.UK One Login (ຜູ້ສືບທອດໂຄງການຢືນຢັນຕົວຕົນ GOV.UK Verify ກ່ອນໜ້ານີ້) ສຳລັບຢືນຢັນຕົວຕົນ. ຂະໜາດທີ່ແພລດຟອມເຫຼົ່ານີ້ບັນລຸເປັນຫຼັກຖານທີ່ຊັດເຈນທີ່ສຸດວ່າຍຸດທະສາດໄດ້ຜົນ: GOV.UK Pay ໄດ້ປະມວນຜົນທຸລະກຳເກີນ £10 ຕື້ໃນປະມານ 1,800 ບໍລິການ — ແລະ ໃນຂະນະທີ່ໃຊ້ເວລາປະມານສີ່ປີເພື່ອປະມວນຜົນ £1 ຕື້ທຳອິດ ປັດຈຸບັນມັນປະມວນຜົນຈຳນວນນັ້ນໃນປະມານຫ້າເດືອນ — ໃນຂະນະທີ່ GOV.UK Notify ໄດ້ສົ່ງຂໍ້ຄວາມຫຼາຍກວ່າ 9 ພັນລ້ານຂໍ້ຄວາມໃນນາມຂອງອົງກອນລັດຖະບານຫຼາຍກວ່າ 1,500 ແຫ່ງ. ທຸກບໍລິການທີ່ນຳໃຊ້ເຫຼົ່ານັ້ນຫຼີກລ່ຽງການສ້າງ, ເຮັດໃຫ້ປອດໄພ ແລະ ບຳລຸງຮັກສາປະຕູຊຳລະເງິນ ຫຼື ທໍ່ສົ່ງຂໍ້ຄວາມຂອງຕົນເອງ.

## ຄະນິດສາດ

```
Build cost per service (no platform) = N services × cost to build,
  secure-assess, and run one payment/notification/identity system

Platform cost = fixed platform build cost
              + marginal cost per adopting service (integration,
                configuration, ongoing platform-team support)

Reuse breaks even once:
  platform build cost < N × (per-service build cost − marginal
  integration cost)

For a mature platform, marginal cost per additional adopter approaches
the transaction/message fee alone — the fixed cost is amortized across
the whole government estate, not one department's budget, which is
why GaaP components are usually funded centrally rather than charged
at full cost-recovery to early adopters.
```

## ຕົວຢ່າງການຄິດໄລ່

**ອົງການປົກຄອງທ້ອງຖິ່ນທີ່ນຳໃຊ້ GOV.UK Pay ແທນການສ້າງປະຕູຊຳລະເງິນເອງ**:

```
Build-your-own estimate:
  PCI-DSS compliance work + integration + ongoing maintenance
  ≈ £85,000 build + £22,000/year maintenance

GOV.UK Pay adoption:
  Integration effort ≈ £12,000 (developer time)
  Transaction fees: government-to-citizen card payments typically
  charged at a small percentage + fixed fee per transaction, no
  separate PCI-DSS burden carried by the council
  ≈ £12,000 one-off, ongoing cost variable with volume, not fixed

First-year saving ≈ £85,000 − £12,000 = £73,000, before counting the
avoided £22,000/year maintenance and the avoided compliance risk of
holding card data in a council-run system at all — this second
category is the security value covered in
public-sector-cybersecurity-value.
```

ຂະຫຍາຍ £73,000 ນັ້ນໄປທົ່ວປະມານ 1,800 ບໍລິການທີ່ປັດຈຸບັນໃຊ້ GOV.UK Pay ແລະ ຕົ້ນທຶນການສ້າງທີ່ຫຼີກລ່ຽງໄດ້ລວມທົ່ວລັດຖະບານແມ່ນຫຼາຍຮ້ອຍລ້ານ — ເສດຖະສາດຂອງແພລດຟອມ ບໍ່ແມ່ນການເຊື່ອມຕໍ່ໜຶ່ງຄັ້ງໃດ ແມ່ນບ່ອນທີ່ມູນຄ່າຂອງຍຸດທະສາດຢູ່ແທ້ຈິງ.

## ຄວາມເຊື່ອມໂຍງກັບວິສະວະກຳຊອບແວ

ລັດຖະບານໃນຖານະແພລດຟອມເປັນຂໍ້ໂຕ້ແຍ້ງໂດຍກົງສຳລັບ [ສ້າງເອງ ຫຼື ຊື້ໃນລັດຖະບານ](../ສ້າງເອງ-ຫຼື-ຊື້-ໃນລັດຖະບານ/): ເມື່ອມີອົງປະກອບຮ່ວມທີ່ຜ່ານການປະເມີນ ແລະ ບໍລິຫານດີ ການສ້າງອັນທຽບເທົ່າເປັນພິເສດແທບບໍ່ເຄີຍເປັນທາງເລືອກ [ຄວາມຄຸ້ມຄ່າເງິນ](../ຄວາມຄຸ້ມຄ່າເງິນ/) ທີ່ດີກວ່າ ແລະ ບໍ່ຜ່ານຂໍ້ 13 ຂອງ [ມາດຕະຖານການບໍລິການດິຈິຕອນ](../ມາດຕະຖານການບໍລິການດິຈິຕອນ/) ("ໃຊ້ ແລະ ປະກອບສ່ວນຕໍ່ມາດຕະຖານເປີດ, ອົງປະກອບຮ່ວມ ແລະ ແບບແຜນ") ເກືອບໂດຍນິຍາມ. ມັນຍັງປ່ຽນຮູບຮ່າງຂອງ [ຕົ້ນທຶນເຈົ້າຂອງທັງໝົດຂອງໄອທີໃນລັດຖະບານ](../ຕົ້ນທຶນການເປັນເຈົ້າຂອງທັງໝົດ-ໃນ-it-ຂອງລັດຖະບານ/): ການນຳໃຊ້ແພລດຟອມແລກປ່ຽນລາຍການທຶນ ແລະ ການບຳລຸງຮັກສາຂະໜາດໃຫຍ່ກັບຕົ້ນທຶນດຳເນີນງານທີ່ນ້ອຍກວ່າ ຜູກກັບການນຳໃຊ້ ເຊິ່ງຄາດການໄດ້ງ່າຍກວ່າ ແລະ ຕັດທຶນໄດ້ງ່າຍກວ່າຖ້າຍົກເລີກບໍລິການ. ການນຳອົງປະກອບກັບມາໃຊ້ແບບເປີດມີຍາດພີ່ນ້ອງໃນ [ມູນຄ່າຂອງຂໍ້ມູນເປີດ](../ມູນຄ່າຂອງຂໍ້ມູນເປີດ/) — ທັງສອງເປັນຍຸດທະສາດການປະຕິບັດຕໍ່ສິ່ງທີ່ລັດຖະບານຜະລິດໜຶ່ງຄັ້ງເປັນໂຄງສ້າງພື້ນຖານຮ່ວມ ແທນທີ່ຈະເປັນຊັບສິນຂອງກະຊວງ.

## ຂໍ້ຜິດພາດທີ່ພົບເລື້ອຍ

- **ການສ້າງໃໝ່ແບບເງົາ**: ທີມງານແອບສ້າງການເຊື່ອມຕໍ່ຊຳລະເງິນ ຫຼື ແຈ້ງເຕືອນຂອງຕົນເອງ ເພາະຂະບວນການເຂົ້າຮ່ວມແພລດຟອມຊ້າກວ່າການເຮັດເອງ — ເປັນບັນຫາຄວາມຝືດຂອງການກຳກັບດູແລ ບໍ່ແມ່ນເທັກໂນໂລຢີ ແລະ ກັດກ່ອນເສດຖະສາດການນຳກັບມາໃຊ້ທີ່ທັງຍຸດທະສາດຂຶ້ນກັບຢ່າງງຽບໆ.
- **ໃຫ້ທຶນທີມແພລດຟອມໜ້ອຍເກີນໄປທຽບກັບມູນຄ່າທີ່ມັນສ້າງ**: ມູນຄ່າຕົກຢູ່ກັບກະຊວງທີ່ນຳໃຊ້ ໃນຂະນະທີ່ຕົ້ນທຶນຢູ່ກັບທີມແພລດຟອມ ສ້າງຄວາມສ່ຽງຂອງການລົງທຶນບໍ່ພໍເຮື້ອຮັງ ເວັ້ນແຕ່ການສະໜອງທຶນຈະເປັນສູນກາງ ແລະ ໄດ້ຮັບການປົກປ້ອງ — ເປັນເວີຊັນໜຶ່ງຂອງໂສກນາດຕະກຳຂອງສິ່ງຮ່ວມ (tragedy of the commons).
- **ວັດຄວາມສຳເລັດຂອງແພລດຟອມດ້ວຍການນຳໃຊ້ຢ່າງດຽວ**: ຕົວເລກການນຳໃຊ້ (ບໍລິການທີ່ເຂົ້າຮ່ວມ, ຂໍ້ຄວາມທີ່ສົ່ງ) ເປັນຕົວຊີ້ວັດນຳ ບໍ່ແມ່ນຫຼັກຖານຂອງມູນຄ່າ; ການທົດສອບແທ້ຈິງແມ່ນການຄິດໄລ່ຕົ້ນທຶນການສ້າງທີ່ຫຼີກລ່ຽງໄດ້ ແລະ ຄວາມສ່ຽງທີ່ຫຼີກລ່ຽງໄດ້ຂ້າງເທິງ.
- **ຖື "ແພລດຟອມ" ເປັນຄຳດຽວກັບ "ໂມໂນລິທ"**: ອົງປະກອບ GaaP ສຳເລັດເພາະແຕ່ລະອັນເຮັດສິ່ງດຽວໄດ້ດີດ້ວຍອິນເຕີເຟດທີ່ແຄບ ແລະ ໝັ້ນຄົງ — ການລວມຄວາມສາມາດທີ່ບໍ່ກ່ຽວຂ້ອງເຂົ້າເປັນ "ແພລດຟອມ" ດຽວສ້າງບັນຫາການສ້າງເປັນພິເສດຂຶ້ນໃໝ່ໃນຂະໜາດທີ່ຕ່າງກັນ.
